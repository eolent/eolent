## Context

[Architecture](../architecture.md) names the main technologies of the reference implementation, and says that the licence terms of each dependency must be checked before it is adopted. Several widely used .NET libraries have moved to restrictive or commercial terms in recent years. Eolent is distributed under the Apache License 2.0 and is meant to be built on by others, including commercially, so a dependency whose terms limit redistribution would pass that limit on to every user.

## Decision

### Dependency policy

1. A runtime dependency of Eolent packages must be available under a permissive licence (Apache-2.0, MIT, BSD or similar, including the PostgreSQL licence, which is of the same kind as MIT and BSD and is the licence of Npgsql) that allows redistribution as part of a commercial product. The only exceptions are named ones, accepted by the maintainer one package at a time, only for packages inside an optional, separate Eolent package that users opt into knowingly (the condition rule 2 sets for restricted libraries), and recorded in the table below.
2. Libraries under copyleft, source-available or paid terms are not used as dependencies of core packages. They may be supported through optional, separate packages that users opt into knowingly.
3. Third-party types do not appear in public module contracts where a thin abstraction is practical. Each abstraction records an exit option: what we would switch to if the licence or maintenance of the library changes.
4. Licences are checked when a dependency is added and re-checked before each release. The result is recorded in the table below. The maintainer who prepares a release runs the re-check. The step is in the [release checklist](../release-checklist.md), which is refined with the release process before the first release. Each code repository MUST run a licence scan in CI from its bootstrap, which checks every pull request against rules 1 and 2. As of 2026-11-20 both code repositories have such a scan from their bootstrap: [eolent-dotnet CI](https://github.com/eolent/eolent-dotnet/blob/main/.github/workflows/ci.yml) and [eolent-react CI](https://github.com/eolent/eolent-react/blob/main/.github/workflows/ci.yml). The job and file names are those repositories' business; the release checklist says how to read the result. The `allowed-licenses.json` of each code repository is the operative allow-list the scan enforces; a licence is added to it only together with an amendment of this ADR that names it. Exceptions to rule 1 for packages that sit in an optional, separate package (on the conditions of rule 2) are named one by one in the table below and in `license-ignored-packages.json` of the repository, and are decisions of the maintainer. A package whose metadata names no licence is recorded in `license-overrides.json` of that repository, with the evidence.

### Choices

| Concern | Decision | Exit option |
|---|---|---|
| Domain events, outbox, job scheduling | Own small abstractions in the kernel (domain event publisher, transactional outbox, job scheduler interface) | Nothing to exit: the code is ours. A broker or bus can be added behind the same interfaces |
| Job engine behind the scheduler interface | Quartz.NET | Another engine behind the scheduler interface, for example a database-polling worker written for Eolent |
| Message broker integration | Not part of the kernel. An optional module may be added later, for example on Wolverine | Optional and separate, so no core change is needed |
| Authentication | OpenIddict embedded in the identity module by default | Any OIDC/JWT-compliant provider, such as Keycloak, Microsoft Entra ID or ZITADEL, because Eolent validates standard tokens only |
| Validation | FluentValidation, used inside module application layers only; the kernel project `Eolent.Kernel.Validation` is the one bridge from a FluentValidation result to the standard error shape, and only the Application layer references it (an architecture test refuses every other layer). Module contracts expose plain request types and the standard problem-details error shape, not FluentValidation types | Replace the validators inside a module with another library or hand-written checks, without changing any contract; replace the one small bridge (`Eolent.Kernel.Validation`) the same way |
| Logging | Serilog, behind `Microsoft.Extensions.Logging` | Any logging provider for `Microsoft.Extensions.Logging` |
| Telemetry | OpenTelemetry | Not applicable: it is the vendor-neutral standard |
| Caching and distributed state | `Microsoft.Extensions.Caching.Abstractions` (`IDistributedCache`), with StackExchange.Redis as the first provider | Another `IDistributedCache` implementation |
| Data access | EF Core (the 10.x line while the repositories target net10.0), with Dapper for hot read paths (outside core modules, or behind a dialect-aware abstraction) | Dapper stays behind repository interfaces, so it can be replaced module by module |
| Frontend UI kit | Tailwind CSS with shadcn/ui components, and TanStack Table for data grids | shadcn/ui components are copied as source, so they are ours. Tailwind and TanStack Table are replaceable inside the kit |
| API client types (frontend kit) | openapi-typescript, as a devDependency of `@eolent/api-client`: it generates the types from the backend's OpenAPI description, the generated file is committed and CI checks it against the description; the client itself is a small typed `fetch` wrapper with no runtime dependency | Orval, or any generator that reads OpenAPI 3.1 and writes TypeScript; the generated file is the only coupling |
| Frontend framework and tests | React 19 (with react-dom), a peer dependency of the kit's packages that use it, never bundled into them; the packages' tests run in jsdom with Testing Library | Not applicable for React itself, which the architecture overview fixes for the kit. The framework-free parts of the kit (`@eolent/api-client`, and the registry, access model and tenant context of `@eolent/core`) do not import it, so they stay usable without it: the React hooks of `@eolent/core` (`usePermission()` and the providers) are a separate entry point of that package, `@eolent/core/react`, and React is an optional peer dependency of the package, needed only by that entry point |
| Browser OIDC client | oidc-client-ts, used only inside the `@eolent/core/oidc` entry point of the kit's core package, as an optional peer dependency; the kit's public API is its own small interface (`AuthSession`: sign in, sign out, current token, user), so no oidc-client-ts type is exposed (rule 3). Authorization code flow with PKCE, the standard-tokens-only stance of the Authentication row | Any OIDC client library, or the identity provider's own SDK, behind the same `AuthSession` interface; applications may also supply their own `AuthSession` and never install the library |

[Architecture](../architecture.md) is updated by this ADR where it lists messaging libraries: the kernel contains no message-bus dependency.

Infrastructure services are not covered by this table. Eolent does not distribute any server software: the Redis cache provider talks to a Redis-compatible server that the deployer chooses and is responsible for, and Redis is optional. Because recent Redis server releases use source-available or copyleft licence options, deployments should check the terms of the server they run, or use a compatible server under a permissive licence such as Valkey (BSD-3-Clause). The kernel depends only on the `IDistributedCache` abstraction.

Development tools are the one place where the pull request scan does not reach: the scan of a code repository checks runtime dependencies, transitive ones included, and not the development install. For a development tool that is never shipped (the openapi-typescript, Testing Library and jsdom rows) the table records the direct dependencies and their licences, and the transitive ones are checked in the maintainer's re-check before each release (rule 4), which lists the licences of the whole install (`pnpm licenses list` in eolent-react). A development tool whose licence the re-check finds outside rules 1 and 2 is replaced or removed before the release. This is a recorded exception, not a claim that the scan covers them.

The licence scan of rule 4 includes transitive runtime packages, so the packages that the rows above bring in (for example Microsoft.Extensions.Options and Configuration.Abstractions through the hosting abstractions) are checked on every pull request in the code repositories; the table records the direct dependencies, and a transitive one only when it needed a separate licence check (for example Mono.Cecil, whose licence is given as a URL).

Licences can change, so this table is a snapshot and must be refreshed under rule 4.

## Consequences

- Eolent owns a small amount of infrastructure code (domain events, outbox, scheduler interface). It is to be covered by the kernel's tests and, once it exists, the conformance suite (planned).
- Users can plug in a different identity provider or job engine without changes to modules.
- Users who want a full message bus can opt into an optional module, or use their own, without it becoming a dependency of everyone.
- A change of any listed library's licence requires a new ADR or an update to this one, and a switch via the recorded exit option.
